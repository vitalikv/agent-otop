# Прототип с открытой языковой моделью

Дата: 31 октября 2026 года. Этап 5б плана: решение и ограничения описаны в [плане](development-plan.md#решение-от-31-октября-2026-года-прототип-с-открытой-языковой-моделью).

Код готов и проверен тестами с подменённой моделью. Прогона на настоящей модели ещё не было.

## Как отвечает бот

1. **Правила этапа 4 без изменений.** Опасность получает проверенный шаблон, а расход считается в диалоге с состоянием. Модель для этого не вызывается.
2. **Выбор разделов.** Модель получает оглавление базы (52 раздела) и возвращает номера до четырёх нужных разделов. Ответ ограничен JSON-схемой, поэтому всегда разбирается. К выбору добавляется лучший результат поиска по словам (`KnowledgeSearch`: BM25, упрощённый русский стемминг, синонимы словаря). Короткое продолжение ищется вместе с предыдущим вопросом.
3. **Ответ.** Модель получает инструкцию, найденные разделы с номерами и последние 9 сообщений диалога. Инструкция требует:
   - опираться только на фрагменты базы;
   - не выдумывать паспортные значения, нормы, цены и коды;
   - уточнять недостающие данные;
   - не давать инструкций по газу, электрике и обходу защит;
   - ставить ссылки вида [2].
4. **Расчёты.** Арифметику модель передаёт инструменту `calculate`. Код вычисляет выражение из чисел, операций, `sqrt` и `pi`, ничего не исполняя как программу. Возможно до четырёх вызовов на ответ.
5. **Источники.** Ссылки перенумеровываются по порядку упоминания и совпадают со списком источников в ответе. Блоки `<think>` удаляются. Если ответ кончается вопросом, он помечается как уточнение.

Состояние диалога расхода передаётся дальше без изменений. Если модель недоступна, сервис отвечает ошибкой 503; правила продолжают работать.

## Запуск

Модели и llama.cpp лежат в `llm/`, эта папка не хранится в Git.

| Модель | Файл | Размер | SHA-256 | Статус |
|---|---|---:|---|---|
| Qwen3-8B, Q4_K_M | `llm/models/Qwen3-8B-Q4_K_M.gguf` | 5,03 ГБ | `d98cdcbd…c5745785` | Скачана и сверена |
| Qwen3-14B, Q4_K_M | `llm/models/Qwen3-14B-Q4_K_M.gguf` | 9,00 ГБ | `500a8806…6b81f0` | Скачать, только если не устроит 8B |

Обе модели берутся из официальных репозиториев `Qwen/Qwen3-*-GGUF` на Hugging Face, лицензия Apache 2.0.

**Через llama.cpp** (основной вариант для сервера). Положите сборку llama.cpp с CUDA в `llm/llama.cpp/` или укажите путь к `llama-server` в `LLAMA_SERVER`. Затем выполните:

```bash
npm run llm:server -- 8b     # или 14b, или путь к .gguf
```

Команда запускает OpenAI-совместимый сервер на адресе из `BOT_LLM_URL` (по умолчанию `http://127.0.0.1:8080`). Все слои модели размещаются на видеокарте; включена поддержка инструментов (`--jinja`). `LLM_PARALLEL` задаёт число одновременных диалогов, `LLM_CONTEXT` — контекст на один диалог (по умолчанию 8192). На этом компьютере автоматическая проверка безопасности не разрешила скачать и запустить llama.cpp, поэтому установка остаётся за пользователем.

**Через LM Studio** (проверка на компьютере разработчика). Подключите модель командой `lms import llm/models/Qwen3-8B-Q4_K_M.gguf` или перенесите файл в папку моделей LM Studio. Загрузите модель с контекстом не меньше 8192 и включите сервер на вкладке Developer (порт 1234).

Перед прогоном через LM Studio клиент нужно адаптировать: у LM Studio нет `/health`, и время он отдаёт в `usage`, а не в `timings`. Пока это не сделано, `npm run llm:eval` сочтёт LM Studio недоступным.

**Сервис бота.** В `.env.local`:

```bash
BOT_LLM_URL=http://127.0.0.1:8080   # для LM Studio — http://127.0.0.1:1234
BOT_LLM_TIMEOUT_MS=120000
```

При заданном `BOT_LLM_URL` сеть определения намерения не загружается: вместо неё отвечает модель. `GET /api/health` возвращает `engine: "rules+llm"`. Клиент чата ждёт ответа до 120 секунд.

## Прогон эталонов

```bash
npm run llm:eval -- --label qwen3-8b            # все 160 вопросов
npm run llm:eval -- --label qwen3-8b --limit 20 # первые 20
```

Вопросы проходят весь путь сервиса: сначала правила, потом модель. Для 10 вопросов с учебным состоянием диалога это состояние передаётся модели как предыдущая реплика.

Отчёт пишется в `data/generated/llm-eval-<label>.md`: вопрос, эталон, ответ, источники и вызовы `calculate`. Там же лежит `.json` со сводкой:
- время ответа (медиана, 90-й процентиль, максимум);
- токены запроса и ответа и их скорость;
- попал ли нужный раздел в запрос — по выбору модели и по поиску слов отдельно;
- указан ли нужный раздел в ссылках;
- совпали ли числа эталона с допуском 3%;
- задан ли уточняющий вопрос там, где эталон уточняет.

Автоматические проверки грубые. Правильность и полноту ответа оценивает человек, читая отчёт.

## Что уже измерено

Поиск по словам без модели на 149 эталонных вопросах, для которых известен нужный раздел базы: нужный раздел первым — 46%, в первых четырёх — 68%, в первых шести — 78%. Мешает расхождение слов: в вопросе «подача, обратка, градусы», а раздел о расходе записан формулами. Поэтому основную роль отводим выбору по оглавлению; насколько он лучше, покажет прогон.

## Ограничения

- **Калькуляторы.** В модель подключён только общий инструмент `calculate`. Проверки применимости из контрактов калькуляторов (подтверждение воды, основание Kv, источник коэффициента расширения) для расчётов кроме расхода выполняет сама модель по инструкции, а не код.
- **Вывод ответа.** Ответ приходит целиком, без постепенного вывода.
- **Эталоны синтетические** и использовались при разработке. Профессиональной проверки нет.
- **Сервер.** Требования к нему и кандидат L40S-16Q описаны в плане; на нём ничего не проверялось.
