# Происхождение локальной инженерной базы

Дата копирования: 30 октября 2026 года.

Рабочая база проекта хранится в [installation-guide](installation-guide/README.md): восемь глав, содержание и список источников. Эталонные ответы и их проверка используют эту локальную копию. Соседний проект для чтения базы, проверки и переноса репозитория не требуется.

## Исходная версия

- Репозиторий-источник: `skeleton-wf`.
- Каталог в исходном репозитории: `docs/heating/installation-guide`.
- Коммит: `ba8f46fcd6afae1e88c762706f7d1789b389c799`.
- Файлы исходной базы на момент копирования не имели незакоммиченных изменений.
- [installation-guide.upstream.json](installation-guide.upstream.json) фиксирует исходные и локальные SHA-256 всех десяти файлов. Перед хешированием CRLF нормализуется в LF.

Инженерные тексты, формулы, числа и их статусы сохранены. В двух файлах, `README.md` и `08-rules-for-automatic-design.md`, ссылки на внутренние планы разработчика превращены в текстовые упоминания с путём внутри исходного репозитория. Эти планы не копируются: они описывают устройство приложения, а не знания бота. В каждом файле манифеста перечислены такие изменения; локальный хеш отличается от исходного только для адаптированных файлов.

Ссылки между главами и на первичные веб-источники сохранены. Веб-паспорта и нормативы не загружаются автоматически и не становятся подтверждёнными заново от факта копирования. [Дополнение по безопасности](../safety-reference.md) остаётся отдельным материалом.

## Обновление

1. Изменения базы в `skeleton-wf` не подхватываются автоматически. Для обновления выбрать конкретный коммит и сравнить его с зафиксированной исходной версией.
2. Проверить инженерные изменения и затронутые эталоны, затем осознанно обновить локальные файлы. Не заменять эту копию ссылкой на рабочую папку другого проекта.
3. В `installation-guide.upstream.json` сохранить новую исходную версию, исходные и локальные хеши и описание адаптаций. Если база меняется только здесь, такие правки нужно явно записать как локальные: их нельзя приписывать прежнему коммиту источника.
4. После смысловой сверки обновить разделы, строки и хеши в [reference-sources.json](../reference-sources.json). Простая замена хешей без чтения изменений не является проверкой.
5. Выполнить `node scripts/check-reference-answers.mjs --write` из корня проекта для обновления документа с ответами, затем `node scripts/check-reference-answers.mjs` для проверки. Проверяются все файлы локальной копии, ссылки, источники, эталоны и расчётные случаи.

## Обновление собранных данных

Подготовлен [весь первый сценарий этапа 3](../stage-3-data.md). Определения и учебные случаи хранятся в `data/definitions` и `data/fixtures`; результаты — `data/generated/knowledge.json` и семь отдельных JSON-файлов калькуляторов, исключённые из Git. Общий файл содержит восемь глав, введения, полные разделы, правила, словарь, объяснения намерений, формулы и эталоны.

1. После описанной выше сверки локальной базы проверить контракты, объяснения, ограничения, численные статусы и затронутые учебные случаи. Изменения формул сверять с арифметическими проверками; новые значения свойств и размеров не считать паспортными без источника.
2. Проверить изменения всех затронутых разделов и их статусов в `knowledge-sections.json`, правил в `engineering-rules.json`, терминов в `terminology.json`, объяснений в `intent-explanations.json` и дополнительных формул в `formula-catalog.json`. Полное восстановление главы из фрагментов должно сохраняться. Неизвестное состояние правила не становится выполненным, учебные значения не становятся паспортными.
3. Выполнить `npm run data:check`: проверяются все эталоны, семь контрактов, дополнительные формулы, учебные случаи, полнота разделов, правил, намерений, ссылок и происхождения. Условные численные примеры отделены от уточнений; изменение источника останавливает подготовку.
4. Выполнить `npm run data:prepare`. Скрипт сохраняет версию исходного репозитория и SHA-256 входов; при несовпадении источников с манифестом останавливается, не переписывая манифест. Все данные проверяются до записи артефактов.
5. Выполнить `npm run data:check-generated`. Повторная сборка из тех же входов должна дать те же файлы. При переносе проекта сначала выполнить `npm run data:prepare`; соседний проект не требуется.

Исходный файл описаний каталога в доступной копии соседнего проекта отсутствует. Словарь использует базу и локально зафиксированную каталожную лексику; это ограничение записано в `terminology.catalog_origin`. При появлении оригинала импортировать его с отдельной версией и хешем, сравнить термины, неоднозначности и ссылки, затем повторить проверки. Сборка не должна незаметно подхватывать соседнюю рабочую папку или выдумывать отсутствующие описания.

Подготовка данных этапа 3 завершена. Загрузка данных в сервис, извлечение параметров, диалог и исполнение операций по запросу пользователя относятся к этапу 4.
