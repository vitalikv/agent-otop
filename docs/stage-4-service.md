# Этап 4: первый рабочий срез

Дата: 30 октября 2026 года. Этап начат; реализован расход воды от вопроса в браузере до расчёта и источника. Собственная нейросеть, обучение, внешние ИИ-сервисы и полнотекстовый поиск не подключены.

## Запуск

```bash
npm install
npm run data:prepare
npm run dev
```

Интерфейс: `http://127.0.0.1:5173`, сервис: `http://127.0.0.1:3001`. Vite проксирует `/api`; Node.js слушает только `127.0.0.1`, адрес не настраивается. Порт задаётся `BOT_PORT`. При разработке настройки из `.env.local` передаются обоим процессам. Код сервиса компилируется TypeScript с наблюдением, Node.js перезапускается при изменении результата компиляции. Отдельные команды и демо-режим описаны в [README](../README.md).

Сервис читает `data/generated/knowledge.json` один раз перед открытием порта. Проверяет версию формата, SHA-256 исходных файлов с нормализацией CRLF, контракт расхода, эталоны, тексты и хеши фрагментов. Отсутствие, повреждение или устаревание данных останавливает запуск. После изменения данных нужно выполнить `npm run data:prepare`, `npm run data:check-generated` и перезапустить сервис.

## Обработка

Классы сервиса: `AppConfig`, `KnowledgeBase`, `ChatController`, `AssistantService`, `TextNormalizer`, `ParamExtractor`, `IntentRules`, `DialogManager`, `HeatingCalculator`. Формулы реализованы кодом, строки формул не исполняются.

Нормализация обрабатывает регистр, «ё», десятичную запятую, Вт/кВт и W/kW, кириллический знак размера `16х2`. Извлечение первого среза поддерживает нагрузку в Вт/кВт, воду и названия смеси, пару `60/40`, отдельные подачу и обратку, охлаждение в К. Отрицания, несколько мощностей и альтернативные режимы не разрешаются выбором первого числа. Словарь остальных инженерных сущностей пока не подключён.

Пользователь должен подтвердить воду и ориентировочный водяной метод. Нагрузка — переносимая расчётная нагрузка участка, а не паспортная мощность котла или радиатора. На шаге нагрузки число без единицы принимается в кВт, на шаге температур — как охлаждение в К; это указано в вопросе. Вне соответствующего шага такое число не задаёт параметр.

Пример диалога:

1. «Посчитай расход для 5 кВт» → уточнение теплоносителя.
2. «Обычная вода, не антифриз» → подтверждение метода.
3. «Ориентировочный расчёт для воды» → уточнение температур.
4. «60/40 °C» → `0,86 × 5 / 20 = 0,215 м³/ч = 215 л/ч`.
5. «А если 50/40?» → `430 л/ч`, нагрузка и метод сохранены.
6. «Охлаждение 20 К» → `215 л/ч`; прежняя пара температур удалена.
7. «Новый расчёт расхода» → параметры сброшены.

Новая пара заменяет прежний перепад, новый перепад — прежнюю пару. Одновременно заданные в одном сообщении значения должны совпадать. Подача ниже обратки и равные температуры требуют уточнения; перестановки и модуля разности нет. Нулевой или отрицательный перепад и отрицательная нагрузка не рассчитываются. Нулевая нагрузка даёт нулевую проектную потребность с оговоркой об обязательном расходе источника.

Сервис не хранит сессий. `Conversation.state` находится в браузере рядом с историей, передаётся с каждым запросом и заменяется только после успешного неотменённого ответа. Переключение и удаление диалогов сохраняют существующую логику. Старые демо-диалоги загружаются без состояния; учебные параметры из эталонов не подставляются. Без `state` короткое продолжение не восстанавливает данные, даже если они были в предыдущем запросе. История передаётся для контекста API, но не используется как источник неявного состояния; клиент передаёт последние 20 сообщений.

## API

`GET /api/health` возвращает `status: "ok"`, `data: "loaded"`, `scenario: "hydraulics.flow"`, `engine: "rules"`, `stateful: false`.

`POST /api/chat`, `Content-Type: application/json`:

```json
{
  "messages": [{"role": "user", "content": "А если 50/40?"}],
  "state": {
    "version": 1,
    "intent": "hydraulics.flow",
    "parameters": {
      "load_kw": 5,
      "coolant": "water",
      "method": "water_approximation",
      "supply_c": 60,
      "return_c": 40
    }
  }
}
```

Ответ — `ChatAnswer` из [shared/chat.ts](../shared/chat.ts): `content`, `sources`, `choices`, `clarification`, `state`; при расчёте также `calculation` с численными значениями и статусом `preliminary_water_estimate`. Источники имеют идентификатор, заголовок и локальную ссылку. `GET /api/sources/:id` отдаёт полный сохранённый раздел с исходным путём как `text/plain`; произвольные файлы не открывает. Ответы в чате выводятся через `textContent`.

Ограничения запроса: 64 КиБ тела, 1–40 сообщений, до 4000 символов на сообщение, до 48000 символов суммарно. Последнее сообщение — от пользователя. Неизвестные поля верхнего уровня и состояния, строковые числа, неизвестные методы и неподдерживаемые версии отклоняются. Клиентский тайм-аут — 10 секунд. Ошибки HTTP: 400, 403, 404, 405, 413, 415, 500. Недоступность API не включает демо-провайдер автоматически.

## Границы

В чат подключён только ориентировочный объёмный расход воды. Для гликоля и неизвестной смеси сообщается, какие свойства и происхождение нужны; коэффициент воды не применяется. Класс калькулятора проверен также на подготовленных структурированных случаях `fluid_properties` и `delta_ratio`, но их текстовый диалог пока не реализован. Свойства из учебных случаев не используются как свойства изделий.

Другая тема получает границу поддержки, даже если в диалоге уже достаточно чисел для расхода. Подбор оборудования, поиск по остальной базе и диагностика остаются следующими задачами. Распознаваемые правилами сообщения о газе, дыме/CO, искрении, кипении, горячей утечке и обходе защиты получают подготовленный первичный шаблон с источниками до расчёта и уточнений. Распознавание ограничено явными формулировками; это не проверенная полнота охвата опасностей.

## Проверки

```bash
npm test
npm run data:check
npm run data:check-generated
npm run build
```

Проверки включают все 30 структурированных случаев расхода из этапа 3, извлечение текста и многошаговые продолжения, сохранение состояния через JSON, смену режима, отсутствие состояния, отрицания и противоречия, источники и HTTP-ограничения, отмену клиентского запроса и отказ запуска при отсутствующей или устаревшей базе. Это синтетическая регрессия разработки, а не независимый контрольный набор и не профессиональная проверка. Проверка интерфейса в настоящем браузере остаётся открытой.

При обновлении статуса этапа 4 изменился источник `policy.service` в плане. Изменения прочитаны и сопоставлены с использующими его SYN-145, SYN-147 и SYN-159: границы поиска подрядчиков, проектирования газопровода и обхода защиты сохранены. В манифесте обновлены полный хеш плана и хеш этого раздела; инженерные материалы и эталонные ответы не менялись.
